# Development

## Prerequisites

Use Node.js 24 or later and npm. The tests use Node's experimental module-mocking support. Install the pinned dependency set from the lockfile:

```sh
npm ci --ignore-scripts
npm run check
```

`check` compiles the contracts, runs the test suite, type-checks the application, and builds the static frontend. It does not submit chain transactions.

## Commands

| Command | Purpose |
| --- | --- |
| `npm run dev` | Vite development server at `http://127.0.0.1:5174` |
| `npm run compile` | Generate contract ABI, bytecode, runtime hashes, and compiler build information |
| `npm run test` | Compile and run the Node test suite |
| `npm run build` | Type-check and build the frontend into `dist/` |
| `npm run preview` | Preview the static build at `http://127.0.0.1:4174` |
| `npm run check` | Run tests followed by the frontend build |
| `npm run deploy:testnet` | Inspect a testnet deployment by default; no broadcast |

The Solidity build pins solc 0.8.37, enables IR compilation and optimization, targets Cancun, and disables embedded compiler metadata. Generated ABI and bytecode are written to `src/generated/contracts.json`; the complete compiler input/output is written to ignored `artifacts/build-info.json`.

## Test coverage

The suite covers derivation-domain separation, first/cached signatures, tampering and replay rejection, concurrent reservations, missing/corrupt journals, shared operation encodings, client recovery state, and CLI state handling. Local EVM tests execute actual Solidity bytecode using signatures generated by the TypeScript client, including native transfers, token calls, and key rotation.

Fixtures contain public synthetic seeds and addresses. They must not be used for funds. Passing tests does not establish an audit, public testnet acceptance, production gas costs, or compatibility with every injected wallet.

## Local browser harness

After compilation, launch the browser fixture:

```sh
npm run compile
node --import tsx scripts/browser-harness.ts
```

Open `http://127.0.0.1:5175`. A prominent banner identifies the local simulation. The harness injects a test wallet and uses an in-memory EVM through an RPC server bound to `127.0.0.1:8547`. It does not forward transactions to a live network or require real keys or funds.

Exercise the actual page flow: create a vault, save a test backup, deposit, send, generate a replacement backup, rotate keys, verify rejection of the old backup, and import the new one. Stopping the process discards the chain state. Browser records may remain; use a dedicated test profile and fresh test keys for subsequent runs.

## Public frontend configuration

Copy [.env.example](../.env.example) to `.env.local` and set only public configuration:

| Variable | Meaning |
| --- | --- |
| `VITE_BSC_MAINNET_FACTORY` | Your verified factory address on chain 56 |
| `VITE_BSC_TESTNET_FACTORY` | Your verified factory address on chain 97 |
| `VITE_BSC_MAINNET_RPC` | Optional public read RPC for chain 56 |
| `VITE_BSC_TESTNET_RPC` | Optional public read RPC for chain 97 |

Factory addresses are empty by default. RPC defaults point to BNB Chain endpoints. Every `VITE_` value is embedded in browser code, so this configuration must not contain private keys or confidential RPC credentials. Restart the development server or rebuild after changing it.

The application separates public RPC reads from injected-wallet transaction submission. Users confirm each live transaction in their own wallet.

## Deploying a factory

Compile first. Provide a dedicated deployment account through the process environment as `DEPLOYER_PRIVATE_KEY`, and optionally set `RPC_URL`. Use a secure environment or secret manager; do not paste a real key into a committed file, frontend variable, or shell history.

```sh
npm run compile
npm run deploy:testnet
```

Without a configured key, dry-run mode only inspects the artifact. With a key, it checks the RPC chain ID and estimates the deployment cost without signing or broadcasting.

To deploy on testnet after funding the deployment account with test BNB:

```sh
npm run deploy:testnet -- --broadcast
```

The script records the transaction immediately in a local `deployments/` file, waits for a successful receipt, and compares deployed runtime bytecode with the compiled runtime hash. Configure the resulting factory address in the frontend for that network. A factory's deployer receives no administrator authority over user vaults.

Mainnet support requires both explicit flags:

```sh
node scripts/deploy.mjs --chain 56 --allow-mainnet --broadcast
```

The extra flags prevent accidental submission; they do not establish production readiness. Review [SECURITY.md](../SECURITY.md) before any live deployment. Updating source or a website does not update existing vault contracts.

## CLI demonstration

`scripts/demo.ts` exercises a deployed factory using shared operation encodings. Inspect its command help before use:

```sh
node --import tsx scripts/demo.ts --help
```

Commands cover initialization, status, vault creation, deposits, token-call demonstrations, spending, replay rejection, and recovery. State-changing commands require `--broadcast`; chain 56 also requires `--allow-mainnet`. Without the required flags they stop before accessing private state or signing.

The CLI stores local secrets, signing state, and independently generated recovery backups in ignored `.local` files. It uses an exclusive process lock. After an abnormal exit, confirm that the original process has stopped and reconcile pending transactions before handling the lock. Never remove signing history to make an old key appear unused. Explicit index skips permanently abandon earlier unused indices.

## Static hosting

Run `npm run build` from the repository root and publish `dist/` with an HTTPS static host. Supply public `VITE_` configuration at build time. No server-side seed storage or signing service is required.

Browser storage is tied to its origin. Changing domain, scheme, port, browser profile, or device does not carry the signing journal with it. A seed backup alone is not a safe journal migration. Plan recovery and continuity before moving an existing deployment's users to a new origin.

## Changes to protocol identifiers

Keep derivation domains, signature labels, namespace metadata, backup formats, and journal identifiers stable. The existing `BscQuantumVault` Solidity names are retained for compatibility. Changing public branding is not a key migration. Any intentional protocol change requires explicit versioning, new test vectors, and a plan for existing accounts.
